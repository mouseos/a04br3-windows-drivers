# BQ24160：Windows向け充電器ポリシーの試作

このディレクトリのポリシーとPIOを既存LC709203F KMDFドライバに統合したが、実機で使用可能な実装ではない。既定ではBQアクセスを含まない。試験ビルドも、Windows用の検証済みファームウェア引継ぎがないためD0開始時にBQへアクセスする前に停止する。`charger.c`は既存の設定が限定条件に一致したときだけ、呼出し側にレジスタ00のTMR_RSTを要求する。電圧・電流・入力選択・充電許可などを変更しない。

## 出自と根拠

- [TI BQ2416xx データシート](https://www.ti.com/lit/ds/symlink/bq24161.pdf)：アクセスで30秒watchdogが開始し、TMR_RSTが必要。タイムアウト時は設定がDEFAULTへ戻りうる。レジスタ00の読取りは過去のFAULTを消費しうる。IDだけではBQ24160とwatchdogのないBQ24160Aを区別できない。
- 端末Linux `CT3_GPL_LGPL_Src/kernel-4.4/arch/arm64/boot/dts/mediatek/a04br3.dts`、`drivers/misc/mediatek/power/bq24160.c`、`drivers/misc/mediatek/power/mt8167/charging_hw_bq24160.c`。GPL実装をコピーしていない。
- [UniXNU-a04br3](https://github.com/mouseos/UniXNU-a04br3) の `package/A04BR3ChargerCore.h`、コミット `0420ce37f0241178a7276784bbc013b0dbba4c95` のMITポリシーをCに移植。期限の検査をキック後にも追加した。
- 既存のLK観測値 `30 00 8c a4 45 51 00 38` はレジスタ設定値であり、実電流の測定値ではない。既存WinPE試験のLC709203F読取りとバッテリー残量表示は充電・外部給電の成立を示さない。

## 単一所有と実装上の条件

I2C2（0x1100b000）の物理リソース、コントローラ、ロック、全トランザクションを単一のWindowsデバイスが所有し、LC709203F（0x0b）とBQ24160（0x6b）はその内部クライアントとする。既存 `lc709203f/wdf_gauge.c` は単独所有の試験版なので、それと別の充電器ドライバを同時起動してはならない。ロックはBQのスナップショット全体とwatchdog書込みを覆う。PIO失敗・タイムアウト後はコントローラ状態不明として共有バス全体を停止し、勝手なリセットやリトライをしない。

将来の所有者はBQへの最初のアクセス前に、リソースの排他、バス初期状態、実行可能な保守ワーカーと単調時計、ファームウェアとの引継ぎ期限、D0終了・スリープ・停止・障害時の継続責任を確立しなければならない。ポリシー部品のdeadline引数は絶対時刻で、ゼロは禁止。10秒間隔の実行を想定し、20秒以上のキック間隔、1秒以上の採取・書込み、時計逆行、期限到達、部分読取り、設定不一致、異常、書込み失敗で停止する。最初の失敗した読取りでもwatchdogが起動した可能性がある。停止は安全な復元を意味せず、ハードウェアのDEFAULT復帰と安全タイマーへの影響がある。キック成功直後でも期限超過と判定する場合があり、キック回数には数えない。

BQと燃料計を一つの共有ロックで直列化する経路、BQの有効な外部入力を検出した場合のBATTERY_POWER_ON_LINE通知、10秒タイマー、D0終了時の同期停止・再開禁止を実装した。BQ採取・保守の失敗時や燃料計の失敗時はバッテリーのサンプルを無効化し、バスを再利用しない。入力切断を含むポリシー不一致でも保守は停止し、BQはDEFAULTに戻りうる。Windowsバッテリークラスには外部電源のunknown表現がないため、BQ情報の失効時はofflineと断定せずバッテリーサンプル全体を無効にする。

ファームウェア引継ぎの実際の保証、Windows RT用KMDFタイマーと電源遷移時の継続、独立したACアダプター通知、障害回復、実機での長時間測定は未実装・未検証。実装されたBATTERY_POWER_ON_LINE通知はシステム全体のACアダプター表示を保証しない。これらの保証がない限りBQに触れない。ポリシー一致値は既存観測の照合に限定し、新たな充電設定値の推奨ではない。

## 引継ぎと電源状態の追加検討

2026-11-04、Windows用EDK II作業ツリー `42db1d06b9650882904128d728080481c53e120a` の `Platform/Benesse/A04BR3Pkg/Drivers/I2c2HandoffDxe/I2c2HandoffDxe.c` を照合した。BeforeExitBootServicesでI2C2のクロック・端子・タイミングを設定するが、BQへのアクセス、watchdog給餌、最終給餌時刻の引継ぎをしない。I2C初期化が成功しても充電器の所有引継ぎ成立を意味しない。対象ファイルにローカル差分はなかった。実機でのLKからWindowsまでの経過時間とBQ状態は不明。

UniXNU-a04br3 `0420ce37f0241178a7276784bbc013b0dbba4c95` の `A04BR3ChargerHandoff.h` は同一起動で確保したADTの128バイト記録に最終給餌・EBS時の物理カウンタ、周波数、結果、fault履歴を保存する。20秒の所有期限と、周波数・時刻・完全なスナップショット・封印を検証し、OS側の時刻原点へ残り時間を保守的に変換する。封印は破損検出であって認証ではない。Windowsの現行UEFIにはこのレコードの生成も、Windowsへの安全な受渡しも存在しない。ADT用の構造をそのままWindowsのACPIや任意のメモリアドレスに置いたとみなしてはならない。

`a04_bq_adopt_handoff` はこの記録の検証と残り期限の保持をCとして実装する独立部品であり、Windowsドライバには接続されていない。呼出し元は起動ごとの信頼できる受渡し、重複しないI2C所有権、同一の物理カウンタを別途保証する。OS単調時刻の採取を物理カウンタ採取より先に行うこと。20秒到達・時計逆行・不正または古い記録・FAULT・設定不一致・演算オーバーフローを拒否する。OSの最初のTMR_RSTまで元の引継ぎ期限を延長せず保持し、採取やスケジューリングの遅延で新しい20秒を与えない。ファームウェアとOSの最初の記録は別々に保持する。現在の `charger_handoff_is_qualified()` は引き続きfalseであり、この部品の存在は有効化の根拠にならない。

Windows側 `a04_bq_step` も、ファームウェアの給餌記録がない場合、または受渡し保留と後続給餌のどちらの状態もない場合、I2C・時計コールバックの前に停止する。未初期化の所有者からの最初のBQ読取りを防ぐための内部不変条件であり、フィールドや記録の値だけで受渡しの真正性・連続責任を証明するものではない。UEFIは別の先行所有者から開始期限を受ける設計で、同じ初回条件をそのまま適用しない。

端末Linux `drivers/power/mediatek/sts_battery_common.c` は通常10秒のbattery timerで、charger存在時にwatchdogを給餌する。suspend準備時はtimerを停止し、resume後にtimer再開と給餌を行う。これはsuspend中の30秒watchdog維持やDEFAULT変化防止の実証ではない。調べたWindows用UEFI、PMIC関連およびLinuxの当該コードには、WindowsのD0不在時にBQを給餌する独立所有者の根拠がない。TOPRGUやPMICのリセットwatchdogはBQのwatchdogとは別で、代用しない。

WindowsのD0終了後、既存タイマーは停止し、直前に開始した通信も停止待ちする。実行中OSが動かないS3・休止・電源断や、共有I2CバスのNACK・busy・タイムアウト、スケジューラ停止中の継続は保証できない。停止時は設定がDEFAULTに戻りうる。現状の「再開しない」は再開の安全保証ではなく、停止を明示する暫定措置。実用化には、ファームウェアからの所有移管と時間原点の検証、D0以外でも動く実証済み保守主体または対象電源状態を禁止できる設計、バス故障時の復旧・給餌責任、シャットダウン/再起動後の引継ぎ、実際のwatchdog期限と電源動作の測定が必要である。Windowsでの時刻・スリープ意味論、ACPIのリソースと重複所有防止も別途検証する。

次回給餌の20秒の上限は、デバイスが書込みを受理し得る区間より前の時刻から数える。書込み完了時刻を使うとI2C転送時間だけ上限が延びてしまう。各採取点でも直前の時刻と比較し、途中の逆行を検出したら停止する。これは観測点間の逆行や停止、システムスリープ中の時刻継続を保証しない。WindowsとUEFIの保守コアを同じ方法で修正し、遅延書込みと採取途中の逆行をホスト模擬で検査している。

物理カウンタの実測比較用 `a04_bq_check_counter_interval` は、独立した基準時計から得た経過時間の上下限と物理カウンタの差を整数で照合する。基準の上下限には各採取時刻の不確かさを含める必要がある。逆行・停止・周波数不正・演算あふれ・範囲外を拒否し、端数は上下へ丸める。基準と対象が同一カウンタに依存する比較は独立した証拠にならない。この関数は指定区間の比較部品であり、D0外の連続性の証明やBQアクセスの許可には使用しない。

3 CPU構成のCPU1はBootShimの限定時間TOPRGU給餌・UART workerで、BQやI2C2の所有者ではない。期限到達で給餌を終了し、システムスリープ・電源断中に実行され続ける保証もない。将来これを保守主体とするなら、寿命と電源状態、コード・共有領域の保持、WindowsとのI2C2移譲時の排他と完了確認、fault時の責任、独立時計による経過測定を別途確立しなければならない。TOPRGU復旧はBQ給餌の代わりではない。

候補の一つは、実証された常時実行環境にI2C2全体を単独所有させ、WindowsのLC709203F要求も期限付きメールボックス経由にする方式である。WindowsがI2C2を同時に直接マップ・操作する方式は採らない。要求の重複や古い応答を拒否し、BQ給餌を燃料計要求より優先し、転送失敗・heartbeat期限切れで両クライアントを無効化する必要がある。ただしバス故障後に給餌を継続する仕組みはこれだけでは存在せず、DEFAULT復帰や外部給電の実際の影響も未知である。S3・休止・電源断で候補環境が動かないなら、その状態を実効的に禁止するか、別の実証済み保守主体が必要である。この候補は未実装で、CPU1やPMICにその能力があると仮定しない。

`owner_broker` はその主体内の単一スレッド用ポリシー試作で、採用済み状態から初回給餌を優先し、10秒の保守期限、最大1秒の残量取得、単調増加する要求番号、要求・主体の絶対期限を扱う。BQ・燃料計読取り失敗、期限超過、時計逆行で両者を停止し、途中・失敗した残量は返さない。期限切れの応答や重複要求も返さず、停止したインスタンスは再開しない。ホスト模擬以外には接続されていない。呼出し側の直列化・専有・定期起動と独立した時計・主体の寿命が前提であり、割込み不能なコールバック、スケジューラ停止、D0外の稼働、故障後の給餌を保証しない。実際のメールボックス、排他移管とキャッシュ整合、電源状態の保証、ユーザー向け故障通知は未実装。

`broker_mailbox` は受信側のコピー済み要求を仲介ポリシーへ渡す試作である。起動世代、単調な要求番号と期限を検査し、失敗応答の残量をゼロにする。要求がない間も主体が別途 `maintain` を期限内に呼ぶ必要がある。停止処理はBQ維持を終了するだけで、I2C2を別主体へ移譲せず、watchdog停止や安全な復元も意味しない。世代番号は認証ではなく、この部品は共有メモリABI・原子操作・キャッシュ整合・主体の生存・期限通りのスケジューリング・排他を提供しない。Windowsクライアントやハードウェアへ接続しない。

移譲準備用の `a04_broker_endpoint_quiesce` は同じ所有者ロックの下で新規クライアント要求を一方向に拒否し、既存所有者の定期 `maintain` は継続できる。呼出し自体はBQへアクセスしない。期限切れや保守失敗では従来どおり停止し、解除・自動再開しない。排他移譲、D0外の実行、障害中の給餌を実現する機構ではなく、現在のD0終了処理にも接続しない。

`a04_broker_handoff` はquiesce済みの旧brokerから、同じ単調時計の原点を使う新所有者へ状態を渡す部品である。最後の成功給餌と旧brokerの次回期限が整合することを確認し、次回期限・主体の寿命・移譲期限の最も早い時刻を初回給餌期限として維持する。受付停止・排出・旧所有の解放・新所有の予約を順に実行し、成功後に旧所有者を停止、状態を新所有者に渡す。途中失敗や時計逆行では両側を停止し、自動復帰しない。呼出し元が旧I2C2ロックを持ち、他CPU・timerを排除し、予約先が関数成功前にI2C2へアクセスしないことが必須である。コールバック成功は実際の排他・実行主体の寿命・故障時の給餌を証明せず、異なる時計原点や電源断をまたぐ移譲には使えない。実ドライバのD0終了からは拒否ゲートの内側に結線され、CPU1には接続されない。

既定OFFのbroker所有者構成は `broker_lifecycle` を介し、採用済み所有者からendpointを結び、給餌timerをendpoint公開前に開始する。定期保守・受信は同じI2C2ロックで直列化する。D0終了ではまず要求受付を閉じ、timer停止後にプラットフォームが証明済みの移譲先を提供した場合のみ移譲部品を呼び、それ以外は停止を記録する。従来の直接所有構成の引継ぎゲートは維持し、broker所有者構成では所有期間・起動epochを返す `owner_platform_start` とD0外の移譲先を返す `owner_platform_successor` が常に拒否する。したがって構成フラグだけで通信や給餌は始まらない。Linuxの `sts_battery_common.c` はsuspend時にtimerを停止しresume後に給餌するが、D0外の継続主体を証明しない。UEFI BQ開始ゲートとWindowsの新規所有者・故障時責任も未解決。停止はwatchdog停止や安全な充電状態への復元を意味しない。

broker所有者のD0開始経路はBQHRのACPI NVSコピーを受け取り、停止記録を拒否する。OS単調時刻を先に取得してから、プラットフォームへ物理カウンタ・周波数・所有期間・起動epochを要求し、証明が揃った場合にだけ `a04_bq_admission_prepare` が既存の受渡し検証を行う。初回給餌期限は所有期間で短縮する。現状の `owner_platform_start` は必ず `STATUS_DEVICE_NOT_READY` を返すため採用には到達しない。BQHR自体の読取りはBQへのI2Cアクセスではない。共有時計、NVSの起動ごとの信頼、排他、D0外・障害時責任を実証するまでこの拒否を外さない。

UEFI機種固有 `I2c2HandoffDxe` は `ArmReadCntPct()` と `ArmReadCntFrq()` を使い、採用可能な記録に最後の給餌・EBS時の物理カウンタと周波数を記録する設計である。ただし現行の `BqAdmissionVerified` は常にFALSEで、BQ未アクセスの停止記録を公開する。NVSページを起動時に確保・初期化しFNVで破損を検査するが、記録には独立した起動nonceや真正性保証がない。Windowsの `KeQueryPerformanceCounter` がUEFIの物理カウンタと同一原点とはソース・実測から確定できない。WindowsのMOU0008資源はACPI上のI2C2 `0x1100b000/0x1000` を排他で要求し、ドライバはraw・translated両方の排他指定を検査するが、PnP管理外のCPU1やファームウェアを排除する証明にはならない。

`A04_BQ_CLOCK_DIAGNOSTIC=1` は `A04_BQHR_DIAGNOSTIC=1` が必要な既定OFFの観測用で、BQHRのACPI NVSコピーの取得前後にWindows QPCと周波数を読む。停止記録、不正、数値不一致、数値上の候補を区別し、候補でも採用やBQアクセスを許可しない。周波数・値が一致しても同一カウンタ、電源状態をまたぐ連続性、起動epoch、I2C2排他の根拠にはならない。既存実測は停止BQHRと残量取得の確認に限られ、QPC対CNTPCTの連続比較は未実施。`KeQueryInterruptTime` はQPCより先に採取するが、複数時計の同一性を仮定しない。

## D0終了時のDEFAULT移行の試作

TIデータシート SLUSAO0H §8.6.3 の02h RESET=1は全設定を既定値へ戻し、DEFAULTへ移行してwatchdogを停止する。§8.3.9は、その後I2Cへread/writeすると約30秒watchdogが再開し、watchdog満了時にもDEFAULTへ移行すると記す。したがってD0外の独立給餌は、設定維持が必須なら必要だが、明示的DEFAULT移行とその条件を許容する場合の唯一の選択肢ではない。RESETの受理後に確認のためBQを読めばwatchdogを再開するため、この経路は読戻しを行わない。PIO完了はDEFAULT移行の独立したハード証明ではない。

§8.3.8–8.3.10によればDEFAULTのVBATREGは3.6 V、ICHARGEは1 A、IN入力は1.5 A、USB入力はD+/D-検出により初期100 mAまたは1.5 A、充電安全タイマーは27分である。満了時には充電が無効になり、DEFAULTでは入力POR・電池着脱・CD切替が再開条件となる。端末の配線、アダプタ、発熱、実電流、バッテリー回復状態がこれらの既定値で適切かは未検証。RESETやwatchdog満了を安全・長時間充電の成功と解釈しない。BQ24160Aには該当watchdogがなく、IDだけでBQ24160と識別できない。

`A04_BQ_DEFAULT_EXIT_EXPERIMENTAL=1` は既定OFFでbroker所有者構成が必要。D0終了で受付を閉じ、タイマーの同期停止と共有I2Cロック取得後、保守期限内の所有者に限り02hへ80hを一度だけ送る。成功・失敗とも所有者を停止し、再試行・BQ読戻しをしない。転送失敗時にはRESETの実行有無とwatchdog状態は不明。BQの引継ぎ開始ゲートは依然閉じ、実機でこの経路が実行可能と主張しない。D0再入後の再取得、旧設定の安全な再設定、27分後の充電継続、電源切断やバス故障時の責任は未解決。これらの実証なしに構成フラグだけでゲートを外さない。

## BATOVP解除の限定部品
