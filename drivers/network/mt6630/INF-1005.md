# INF1005: NDIS必須keywordの配置修正

run33の回収service.log（fresh39で見えた旧run33 record）の
RUN=0000F6F2/ID=0000000Dで、EVT107=0x1f(Code31)、EVT109=0xc000014dと
選択version2026.11.6.1003を確認した。WLAN Open0/Enum0/INTERFACES0/EXIT3は主担当回収結果。
これは1003の結果で、未normal-bootのrun38/1004の失敗として使わない。

SDK ntstatus.hの0xc000014dはSTATUS_REGISTRY_IO_FAILED。
STATUS_INVALID_LEVELは0xc0000148であり、level/revision不一致を示す値ではない。
このProblemStatusだけからminiport内のどのregistry APIか、storage障害か、
NDISの初期化前設定読み取りかを断定しない。旧1001/14:44 SetupAPI記録も原因判定に使わない。

## sourceで確定した欠落

1003/1bd250cと1004/3ca98c9のINFは、必須3keywordを[Install.NT.HW]のAddRegから
hardware keyへ置くだけで、DDInstall自身には定義していなかった。
C側NdisMSetMiniportAttributesで値を設定することは、NDISがInitialize前に必要とする
INF登録を代替しない。この配置は以前のINF確認で見落としていた。

Microsoft公式[Standardized INF Keywords](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/standardized-inf-keywords-for-network-devices)
はconnectionless NDIS6以降に*IfType/*MediaType/*PhysicalMediaTypeを必須とし、
欠落時はMiniportInitializeExを呼ばないと明記している。
[AddReg directive](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/inf-addreg-directive)
でもDDInstall.HWのHKRはhardware keyと定義され、DDInstallのsoftware keyと異なる。

固定公式sample tree d49bb7d72f3651952b2b6e4ad28d14fe2247eb69で比較した。

- [netvmini630.inf](https://github.com/microsoft/Windows-driver-samples/blob/d49bb7d72f3651952b2b6e4ad28d14fe2247eb69/network/ndis/netvmini/6x/630/netvmini630.inf): [NetVMini.ndi]直下に必須3keyword。
- [Native SDIO sample netrtwlans.inf](https://github.com/microsoft/Windows-driver-samples/blob/d49bb7d72f3651952b2b6e4ad28d14fe2247eb69/network/wlan/WDI/PLATFORM/WinInf/SDIO/x64/netrtwlans.inf): [RTL8723bs.ndi.NT]直下に71/16/9。HW節は別のfilter registration用途。sampleのx64 code/WDI/FWをARM32へ流用する根拠には使わない。

1005は既存[Install.NT]へ以下のclass固有DDInstall directiveを移し、
誤ったNetHardware AddReg経路を除去する。値とadvertised機能は変更しない。

```ini
*IfType=71
*MediaType=16
*PhysicalMediaType=9
```

INF versionだけを11/06/2026,2026.11.6.1005へ上げる。NDIS/C/firmware/PSP/鍵/親コードの
推測変更、未知opcode、registry ACL迂回は追加しない。
これは一次仕様とsampleに基づくINF修正。run33のsole rootcause確定、
NDIS初期化・WLAN列挙・scan成功の実測ではなく、新しい実機確認が必要。

## SYS再build不要の固定repackage

署名回収済み1004/3ca98c90f10bd977fa79a32cbc54d7c799173899 SYSの実hashをhostで再確認:
`fdcc71a27b8b5df38f679934b34c1bd8dc567405ae0a6b878c6ae622b2612aba`。
1005はこのsigned SYSをそのまま使い、INFとCATだけ更新できる。親1006も再build不要。

```powershell
& .\tools\ci\package-mt6630-runtime-1005.ps1 `
  -SignedSys <回収済み署名1004のmt6630-runtime.sys> `
  -OutputDirectory "$PWD\build\native1005-signed-new"
```

scriptはclean固定source、上記signed SYS hash、3caからC/header差分無し、
DDInstallの3directiveとINF versionを検査する。SYS署名を検証し、fresh CATを生成・署名して
membershipを検証、SYSが全byte不変であることを最後も検査する。
既存runnerのBCBF開発鍵を使い、証明書生成・SYS再署名・kernel/親再compileは行わない。
新manifestはINF source commitとbinary_source_commit=3caを分け、再buildしたと偽らない。
生成物・tempは新規checkout内directory。実機/runner操作を行うscriptではない。

同SYSなのでcheckpoint.driver_build=1004は正しい。INF/selected Class DriverVersion=1005と
binary hash/3ca sourceを区別して記録する。checkpointに表示される1004だけで
DriverStore旧版再利用と判断しない。元1004の署名bundle・recipeは保持する。

## 次の確認と制限

- 標準PnP installerで新INFをstage/bindし、selected Class DriverVersion1005、
  signed SYS実hash、mandatory keyword登録、CM/ProblemStatusを主担当が確認する。
- native replayed SYSTEMで新checkpoint世代とDriverEntry/Initializeを確認。
  record不存在はInitialize成功にしない。pre-Initialize拒否ではInit recordがない可能性がある。
- 0xc000014dが残ればcheckpoint/CM/service LastDiagnosticを照合し、
  仮説をsame-rootcauseとして反復しない。NTSTATUS名だけから具体I/O障害を捏造しない。
- 今回はdirect DDInstall/値/versionのhost検査、固定署名SYS hash照合、PS Parser、
  C/header差分無しを確認。Inf2Cat/CAT署名と実インストールは主担当工程。
