# GE8300のsoftware GDI shadow対応

基点は4a952787f1befccd5c580e826b109fb9decc9c80、候補INFは0.0.3.76。ドライバ作成・context作成でWDK8.1のSystem/Gdi bitsを受理する。SupportKernelModeCommandBuffer、RenderKm、hardware cache-coherent apertureは広告しない。

## 対応範囲

同format・同解像度のA8R8G8B8またはX8R8G8B8 shadow/shared primary間の双方向Bltを扱う。部分矩形はSrcRect/DstRectから平行移動を求め、実コピー範囲はpDstSubRectsに従う。stretch、color conversion、同一allocation内コピー、ColorFill、flip、NULL endpoint、未知flagsは未対応として失敗する。

TQは既存のpoint samplingと4channel UNORM8 packingを用いる。整数load/storeによるraw bitwise copyではない。X8を含む実GPU全byte一致、通常GDI/DWMの実動作はこのソース検証では確認していない。

## captureと完了の所有権

Presentは全RECTを検証してNonPagedへコピーし、残りのRECT配列を1個のscheduler job/ticketに保持する。DMA/private/patchの容量不足はjob作成前に返し、MultipassOffsetは進めない。足りる場合は残り全RECTを1jobに取り込みoffsetを末尾へ進める。元のOS配列は保持しない。countとallocationサイズの乗算は割当て前に検証する。

pending payloadはdraw/copyのpointer unionで、サイズ・offsetは旧構造と同一。kind==COPYのpayloadをdraw commandとして解釈しない。両方とも同じNonPaged所有権・解放tagを使い、既collectorはstate0のpayloadだけをPASSIVEで解放する。

中間regionの実GPU/SLC/CPU可視化完了時だけindexを進め、state9へ戻す。実完了IRQから既DPC/workerへ継続を渡す。OSのDMA-completed通知とlast_completedは最終regionまで更新しない。途中failure・不確実な可視化は既engine失敗経路でpoisonし、refs/capture/MDLを保持する。停止に失敗しても解放しない。既owner drain proof後のretirementとcollectorが最終解放を行う。

state9は同じscheduler DMAの未完了部分。engineのactive判定、continuation claim、prepare-readyに含め、preempt要求が出てもそのDMAを最後まで処理できる。後続DMAは追い越さず、preempt完了は元DMAの最終完了後となる。

1Presentに33RECT以上あっても1枠だけ使う。独立したPresent/Renderを33本以上未送信で保持する固定32job poolの上限を解消したものではない。

## 増分ビルドの閉包

変更TUは次の8個。native3C、module4Cと1C++。SDK、UMD、FWを再構築しない。既372 KMD archiveの5memberと既30cb native archiveの3memberを置換してrender SYSをリンクする。

- kmd_objects.c: GDI bits、A8/X8 shadow、state9診断。
- kmd_clear.c: rectangle batch、native prepare/完了の接続。
- clear_engine.c: 双方向copyとstate9のscheduler処理。
- miniport.c: GPU376実行時識別子。
- unified_display.cxx: X8 shared primary layout。
- native_owner_factory.c: copy専用staging source retarget。
- native_owner_factory_runtime.c: 独立destination選択。
- windows_native_copy_storage.c: A8/X8・renderable/staging destination。

ヘッダーのunionとstate定数は構造体のサイズ・offsetを変えない。retained consumerの扱いは以下のとおり。

| retained TU | state9/payloadへの扱い |
| --- | --- |
| display_adapter356.c | source_lockedの`state && state != 4`がstate9をbusyとし、unmap前の待機に含める。payloadは解釈しない。 |
| preempt.c | jobのcontext/retired_generationを照合し、状態遷移は変更済みengine関数へ委譲する。state9のcancelはbusyで保持。 |
| lifecycle.c | 個別state/payloadを解釈せず、owner proof後のengine retirementとcollectorを使う。 |
| miniportのworker経路 | service_pending/DPCからengineのclaimへ渡す。miniport自体は識別子変更で再コンパイルする。 |
| その他のKMD/native/transport TU | jobstate/pendingを直接読むconsumerは上記以外にない。engine/adapterの実レイアウトは変えない。 |

実COFFでdisplay_unified_display.objはKMDにのみ存在し、transport archiveにはない。transportの署名済372、UMD、FWを保持し、最終採用時にmainが署名packageと実link inputsを照合する。

`tools/ci/build-ge8300-gdi376-incremental.py`は既372のarchive parser等を再利用し、正規pinsと元compile flagsを使う。pathだけを既task入力へ移す。--plan-onlyはarchive/pins/member対応の検証であり、コンパイル成功を意味しない。署名・実機操作はこのrecipeに含めない。
